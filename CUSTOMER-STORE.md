# Изолированный клиентский магазин

Магазин разрабатывается в отдельном форке. Действующие административный бот,
клиентский бот и кабинет продолжают работать до отдельной приёмки замены.
Основное техническое задание административного проекта не изменяется.

Этот кандидат добавляет постоянный реестр независимых подписок, выбор в боте
и кабинете, привязку платежа к конкретному подключению и сверку неопределённых
результатов. Режим включается отдельно; перед рабочим переключением нужна приёмка
на копии данных установленного магазина.

## Состояние функций

| Возможность | Состояние кандидата |
| --- | --- |
| Тарифы, настраиваемый тест, способы оплаты, подключение приложений | Существующий функционал исходного проекта; отдельная приёмка ещё не проведена |
| Несколько аккаунтов одного клиента | Отдельные подключения, сроки и условия; список и карточки в Telegram, выбор в двух встроенных дизайнах кабинета |
| Заказы и платежи | Снимок выбранного подключения; смена меню, вкладки и повтор webhook не перенаправляют оплату |
| Неопределённая выдача | Постоянный журнал; сверка администратором без повторного продления; однократный возврат внутреннего резерва при отмене |
| Неоднозначный поиск по Telegram ID | Выдача/продление останавливаются вместо выбора первого аккаунта |
| Перенос рабочих аккаунтов | Только документ для проверки, без импорта и изменения панели |
| Старый кабинет, балансы, поддержка | Продолжают жить в текущем проекте; переноса между разными схемами баз пока нет |
| Изолированный образ | Отдельный непривилегированный процесс, свои данные, без Docker-сокета |

## Несколько независимых подписок

`MULTI_SUBSCRIPTIONS_ENABLED=true` включает новый режим. По умолчанию `false`:
существующий сценарий одной подписки остаётся доступным. Если заказы нового режима
уже выставлены, отключать его до их завершения не следует.

«Мои подписки» показывает все аккаунты с достоверным Telegram ID клиента.
Выбор открывает отдельную карточку, инструкции, устройства и продление этого
подключения. Кабинет сохраняет выбор для каждой вкладки. Старые кнопки карточки
и ранее выставленные счета сохраняют исходное подключение. Сервер проверяет
владельца каждого запроса, даже если клиент подменит заголовок или кнопку.

Обнаружение читает до 100 аккаунтов; неполная страница или чужой владелец
останавливают обработку. Имена и почта из панели не используются для автоматического
доказательства владения. Для старого клиента без Telegram ID сначала нужна
проверенная администратором привязка в панели. Документ `migration-plan` сам
такую привязку не применяет. Существующая подписка, даже истёкшая, исключает новый
триал. Длительность теста, тарифы и лимиты задаются штатными настройками магазина.

Снимки счетов и журнал выдачи сохраняются в SQLite/PostgreSQL, экспорте и резервных
копиях. При обрыве связи подписка блокируется для повторной выдачи до сверки.
В административном меню есть «Сверка выдачи подписок»: подтверждение считывает
срок через API и записывает уже состоявшийся платёж, не продлевая его повторно.
Если срок отличается от сохранённого, автоматическое подтверждение отклоняется.
Для первого нового аккаунта без постоянной привязки нужна ручная проверка;
подтверждение выдачи из этого меню доступно после отдельного сопоставления.

Отмена требует отдельного подтверждения администратора: услуга не была выдана
либо условия вручную исправлены в панели. Внешний платёж перед отменой нужно
вернуть у провайдера. Внутренний резерв возвращается на баланс транзакцией один
раз. Старые платёжные уведомления отменённую операцию не исполняют заново.
Кнопки подтверждения действуют 3 минуты и после перезапуска требуют открытия меню.

Ограничения этого кандидата: у клиента по-прежнему одно автопродление из исходной
схемы, закреплённое за конкретным подключением. Одновременное автопродление всех
подписок не реализовано. Статический Tribute без идентификатора подключения при
нескольких аккаунтах скрывается. Покупка ещё одного нового независимого подключения
при наличии старого пока не добавлена: поддержаны несколько существующих аккаунтов
и первоначальное создание. Баланс общий для клиента, сроки и условия раздельные.

## Проверка миграции без сети

Команда `migration-plan` читает полный локальный экспорт панели и необязательные
подтверждённые администратором сопоставления владельцев. Она не обращается к API,
не импортирует данные, не выдаёт тест и не продлевает подписки.

```sh
go build -o .private/migration-plan ./cmd/migration-plan
.private/migration-plan \
  -inventory deploy/inventory.example.json \
  -claims deploy/claims.example.json \
  -out .private/migration-review.json
```

Перед сборкой создайте `.private`. Для реальных данных используйте только этот
приватный каталог, защищённый правами владельца. На Windows дополнительно
ограничьте доступ средствами ACL: режим Unix 0600 там не задаёт ACL.
Ни экспорт, ни документ проверки не публикуются. Вывод команды не содержит
имён и идентификаторов клиентов. Существующий файл результата не перезаписывается.

Формат входа показан в `deploy/inventory.example.json`. `complete: true` —
утверждение оператора о получении всех страниц; `total` должен совпадать с числом
аккаунтов в панели и длиной массива. Команда проверяет согласованность документа,
но не может доказать полноту выгрузки без обращения к источнику.
Используются исходные UUID либо числовые ID поддерживаемых версий API.

Все аккаунты с одним положительным `telegramId` попадают в одного клиента,
каждый со своими сроком, трафиком, устройствами и сквадами. Лимиты и даты не
объединяются. Имя и непроверенная почта не являются доказательством владения.
Для аккаунта без Telegram ID нужен проверенный `tg:ID` либо `email:адрес` в claims.
`verified: true` ставит администратор после проверки владельца; это не результат
автоматического подтверждения программой. Противоречащие друг другу claims или
владельцу панели значения блокируют сопоставление.

Коды завершения: `0` — все аккаунты распределены; `2` — документ создан, требуется
разбор несопоставленных аккаунтов или конфликтов; `1` — вход или запись отклонены.
Даже код `0` не означает разрешение импорта: исполняющего импортера пока нет.
Все существующие клиенты получают `trialEligible: false` в документе.
Ссылки подписок, пароли, описания, почта из панели и HWID устройств не копируются.

## Изолированный пилот

Используйте только `deploy/compose.pilot.yaml` и `deploy/Dockerfile.pilot`.
Штатный Compose исходного проекта предоставляет доступ к Docker хоста и для
этого пилота не предназначен. Здесь отдельные сеть и том, порт кабинета привязан
к localhost, нет доступа к каталогам либо контейнерам панели. Локальный режим
доступа к панели и установка базы/прокси из бота в этом образе не поддерживаются:
подключайте панель по HTTPS через её API, база пилота — SQLite.

Подготовьте `deploy/.private/pilot.env` по примеру `deploy/pilot.env.example`.
Токен отдельного тестового клиентского бота сохраните в
`deploy/.private/customer-bot-token`: файл должен читаться UID 10001, но не другими
пользователями. Каталоги с секретами защищаются на хосте и исключены из Git и
контекста сборки. Один и тот же токен не используют два получателя одновременно.
Для пилота нужен отдельный тестовый бот; рабочий переключается только при переносе.

```sh
docker compose --env-file deploy/.private/pilot.env \
  -f deploy/compose.pilot.yaml --profile pilot config --quiet
docker compose --env-file deploy/.private/pilot.env \
  -f deploy/compose.pilot.yaml --profile pilot build
```

`up -d store` выполняется той же командой после подготовки тестового токена.
Мастер первоначальной настройки должен быть закончен до успешной проверки
`/healthz`. Нездоровый health сам по себе не перезапускает процесс.
Автоперезапуск для пилота выключен. Это не режим работы магазина в production.
Переменные `.env` старого проекта сюда не копируются.

Поддержаны `BOT_TOKEN_FILE`, `SECRET_KEY_FILE`, `DATABASE_URL_FILE`,
`CADDY_AUTH_API_TOKEN_FILE`. Укажите либо переменную, либо соответствующий файл.
Файл ограничен 4096 байтами, должен быть обычным непустым файлом без перевода строк
внутри; символьные ссылки отклоняются. Ошибки не выводят путь или значение.
Одно завершающее LF/CRLF удаляется. Значение существующего `SECRET_KEY` из окружения
сохраняется побайтно: при переносе нельзя заменить ключ и потерять доступ к базе.

Для резервирования остановите только сервис магазина и скопируйте целиком его
отдельный том, включая SQLite WAL и `secret.key`, вместе с приватными настройками
и зафиксированной ревизией образа. Архив содержит секреты, хранится зашифрованно
вне Git. Восстановление сначала проверяется на новом томе без сети. Откат образа
не должен восстанавливать старую базу поверх актуальных оплат.

## Приёмка перед переносом

1. На копии базы проверить список двух подписок одного клиента, старую карточку,
   две вкладки кабинета, оплату A после выбора B и отказ чужому владельцу.
2. Проверить восстановление резервной копии вместе с журналом незавершённых
   операций и запрет повторной выдачи после восстановления. Старые callback-токены
   после типизированного переноса могут требовать обновления меню; полный бэкап
   сохраняет их. Возврат образа не означает возврат базы к старым оплатам.
3. Проверить однократный тест, действующие тарифы и привязку почты к Telegram.
   Новые лимиты не должны заменять уже проданные условия другого подключения.
4. Проверить тарифную линейку и платежи на синтетических заказах: дубликаты,
   отказ, возврат, неопределённый результат, подтверждение скриншота человеком.
5. Проверка «Подключиться»: приложения, инструкции, импорт выбранной подписки,
   запасная ссылка и изолированная поддержка.
6. Явный план переноса старого кабинета и истории обращений. Общий Telegram ID
   сам по себе не переносит баланс, пароль или историю между разными базами.
7. Приёмка, резервирование, переключение одного получателя и план возврата.

Для цифровых услуг внутри бота/Mini App платёжный сценарий должен учитывать
[правила Telegram Stars](https://core.telegram.org/bots/payments-stars).
RUB и USDT для обычного веб-кабинета проектируются отдельно с учётом правил
провайдера; наличие ссылки на внешний сайт само по себе не является исключением
из правил оплаты внутри Telegram. Чек/скриншот не подтверждает деньги автоматически.

Подготовку и выдачу подписки выполняет проверяемый платёжный код, а не ИИ.
ИИ-поддержка и автоматические изменения инфраструктуры в этот кандидат не добавлены.
